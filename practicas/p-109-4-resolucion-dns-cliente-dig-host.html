1. De qué va

Aprende a configurar, auditar y resolver problemas en la capa de resolución de nombres DNS del cliente Linux. Comprende el orden de precedencia establecido por el archivo maestro `/etc/nsswitch.conf` (`hosts: files dns`), la sintaxis y directivas clave de `/etc/resolv.conf` (`nameserver`, `search`, `domain`, `options`), y domina la diferencia conceptual y práctica evaluada con insistencia en LPIC-1 entre utilidades de resolución del sistema (como `getent hosts` y `ping`, que leen `/etc/hosts`) frente a clientes DNS puros (como `dig` y `host`, que interrogan directamente a los servidores DNS sin consultar jamás `/etc/hosts`). Adaptado para funcionar con el resolver local de la máquina virtual si no hay conexión a Internet.

2. Qué aprenderás

  • Configurar y comprobar las directivas `nameserver`, `search` y `domain` en `/etc/resolv.conf`.
  • Interpretar y auditar el orden del conmutador Name Service Switch en `/etc/nsswitch.conf`.
  • Instalar las herramientas DNS estándar de Debian (`bind9-dnsutils`).
  • Realizar consultas DNS concisas con `host` (registros A, AAAA, MX, NS) apuntando al resolver del sistema o servidores públicos.
  • Realizar consultas avanzadas con `dig` (`+short`, `+trace`, registros inversos PTR con `-x`).
  • Demostrar experimentalmente la trampa clásica de examen entre `getent hosts` y `dig`/`host` mediante un nombre ficticio.
  • Ejecutar la limpieza segura y garantizada de `/etc/hosts` tras la prueba de resolución.

3. Antes de empezar (≤ 5 min)

1. Inicia sesión en tu máquina virtual Debian 12 con el usuario habitual alumno.
2. Verifica que tienes permisos de administración ejecutando sudo -v en la terminal.
3. Asegúrate de estar trabajando sobre la instantánea limpia 00-base-limpia.
4. **Instala las utilidades de cliente DNS**: En Debian 12, los comandos dig y host vienen en el paquete bind9-dnsutils. Instálalos con: sudo apt update && sudo apt install -y bind9-dnsutils.
5. Comprueba que los comandos dig y host se ejecutan sin errores con dig -v y host -V.

4. Misiones Guiadas Paso a Paso

Misión 1 — Inspección y Configuración de /etc/resolv.conf y Orden de NSSwitch

Examinaremos los dos archivos que controlan la resolución de nombres del sistema operativo: `/etc/resolv.conf` (que especifica a qué IPs enviar las consultas DNS) y `/etc/nsswitch.conf` (que determina si se consulta primero el archivo local `/etc/hosts` o los servidores DNS).

¿Qué significa cada parte del comando?

  • `hosts: files dns`: En `/etc/nsswitch.conf`, indica al subsistema de resolución C (glibc) que busque primero en `files` (el archivo estático local `/etc/hosts`) y, solo si el nombre no se encuentra allí, consulte a los servidores `dns`.
  • `nameserver IP`: Dirección IP del servidor DNS recursivo al que se enviarán las peticiones (se pueden definir hasta 3 como respaldo). En VirtualBox NAT suele ser `10.0.2.3` o la IP de tu router.
  • `search dominio.com`: Lista de dominios que se añaden automáticamente cuando el usuario consulta un nombre que no termina en punto (nombre no cualificado).
  • `options timeout:2 attempts:2`: Opciones de ajuste del resolver glibc.
👀 Qué debes observar: `grep '^hosts:' /etc/nsswitch.conf` mostrará típicamente `hosts: files dns` (o variantes con `mdns4_minimal`). `/etc/resolv.conf` mostrará al menos una línea `nameserver`.

Misión 2 — Consultas DNS Directas, Inversas y Registros Específicos con dig y host

Utilizaremos `host` para consultas rápidas y concisas, y `dig` para auditorías técnicas profundas. Consultaremos direcciones IPv4 (tipo A), servidores de correo (MX) y realizaremos una resolución inversa (PTR) a partir de una dirección IP. Si el aula no dispone de conexión activa a Internet exterior en ese momento, las consultas utilizan el resolver local o localhost de forma segura sin bloquearse.

¿Qué significa cada parte del comando?

  • `host -t TIPO dominio`: Solicita un tipo de registro específico (A, AAAA, MX, NS, SOA, TXT).
  • `dig +short`: Suprime cabeceras y comentarios, mostrando únicamente la respuesta final limpia (ideal para scripts bash).
  • `dig dominio`: Muestra las cuatro secciones estándar de una respuesta DNS:
  • *HEADER*: Flags (QR, RD, RA) y código de estado (`NOERROR`, `NXDOMAIN`).
  • *QUESTION SECTION*: La consulta enviada.
  • *ANSWER SECTION*: Registros devueltos con su TTL (Time To Live).
  • *AUTHORITY / ADDITIONAL*: Servidores autoritativos y estadísticas de consulta.
  • `dig -x IP`: Realiza la búsqueda inversa en la zona especial `in-addr.arpa` para encontrar el nombre de host asociado a esa IP.
👀 Qué debes observar: `dig` devolverá `status: NOERROR` y los registros solicitados junto con el tiempo de consulta (`Query time`) y el servidor que respondió.
📸 Captura 2: Salida de `host -t MX lpi.org` (o `SOA`) y de `dig -x` inverso. Guarda como `109-4-C2-dig-host-queries.png`.

Misión 3 — Demostración de la Trampa de Examen: getent hosts vs dig/host y Limpieza de /etc/hosts

Comprobaremos de forma práctica la diferencia crucial evaluada en LPIC-1: `getent hosts` y `ping` utilizan la biblioteca de resolución del sistema operativo (que lee `/etc/hosts` según `/etc/nsswitch.conf`), mientras que `dig` y `host` son clientes de red que interrogan exclusivamente a los servidores DNS configurados y nunca leen `/etc/hosts`. Al terminar, limpiaremos de forma estricta la entrada ficticia de `/etc/hosts`.

¿Qué significa cada parte del comando?

  • `host servidor-fantasma.lpic.lab`: Falla con `Host ... not found: 3(NXDOMAIN)` porque envía un paquete UDP a los DNS en `/etc/resolv.conf`, los cuales desconocen ese nombre privado.
  • `getent hosts servidor-fantasma.lpic.lab`: Tiene éxito inmediato y devuelve `192.168.10.99` porque consulta `/etc/nsswitch.conf`, el cual le indica buscar primero en `/etc/hosts` (`files`).
  • *Conclusión fundamental de examen*: Si un comando utiliza la glibc (`ping`, `ssh`, `curl`, `getent`), obedece `/etc/hosts`. Si es una herramienta de diagnóstico DNS (`dig`, `host`, `nslookup`), ignora por completo `/etc/hosts`.
  • `sudo sed -i '/.../d' /etc/hosts`: Borrado seguro y atómico en el archivo maestro de hosts.
👀 Qué debes observar: `host` devolverá error (NXDOMAIN), mientras que `getent hosts` mostrará `192.168.10.99 servidor-fantasma.lpic.lab`. Al ejecutar el comando de limpieza, `getent hosts` dejará de devolver la entrada.

5. Mini-Reto Final de Autonomía (5 min)

Demuestra lo aprendido: Un técnico de soporte añade la línea `10.50.1.20 IntranetEmpresa` en `/etc/hosts`. Sin embargo, cuando los usuarios ejecutan `ping IntranetEmpresa`, el comando devuelve `ping: IntranetEmpresa: Nombre o servicio desconocido`. El técnico comprueba que `/etc/hosts` está bien escrito. ¿Qué archivo del sistema debe revisar y qué directiva errónea podría estar provocando que Linux ignore `/etc/hosts`?

💡 Ver pista desplegable si te atascas
Revisa el archivo Name Service Switch y el orden de los motores de búsqueda de hosts.
✅ Ver solución oficial explicada
Debe revisar el archivo /etc/nsswitch.conf. La línea hosts: probablemente contenga hosts: dns (habiendo omitido la palabra clave files) o tenga una directiva condicional errónea tipo hosts: dns [NOTFOUND=return] files. Para solucionarlo, debe asegurarse de que files figure en primer lugar: hosts: files dns.

7. Si algo falla (Solución rápida)

Comandos `dig` y `host` no encontrados
Instala el paquete oficial en Debian 12: `sudo apt update && sudo apt install -y bind9-dnsutils`.
Error de timeout al consultar dominios externos (lpi.org)
Si tu máquina virtual no tiene salida a Internet exterior, el resolver de VirtualBox tardará en responder o dará timeout. Utiliza la IP del resolver local de la VM (revisa `cat /etc/resolv.conf`, típicamente `10.0.2.3`) o prueba resolviendo `localhost`.
Queda la entrada de prueba en `/etc/hosts`
Elimínala manualmente ejecutando `sudo sed -i '/servidor-fantasma/d' /etc/hosts`.
Restaura tu máquina a estado limpio
Al terminar las pruebas, restaura el snapshot `00-base-limpia` en tu hipervisor.
